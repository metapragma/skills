### Investigation

**You own the answer.** The work is read-only. It produces a cited explanation
or a recommendation, not a code change.

1. Run [how](../../how/SKILL.md) over the subsystem in question. For a question
   about why something is built this way, also run [why](../../why/SKILL.md).
   For facts that live outside the repository, such as library or API
   behavior, run [research](../../research/SKILL.md).
2. For a choice between alternatives, add a tradeoffs table and your
   recommendation. For "are we sure?", give your real judgment and its reasons.
3. Check each load-bearing claim against the code or a run, and cite it as
   `file:line`, a command, or an artifact.

When the answer leads to a change, stop at the answer. Name the playbook the
change belongs to, and start it only on the user's go-ahead.

**Reply:** the explanation or recommendation, its citations, and the open
questions. Push back when the premise of the question is wrong.
